# Шаги реализации: RAG-документация для OpenCode

Дата: 2026-04-27

## Общие границы

Реализация ведётся на TypeScript. Код должен быть читаемым, поддерживаемым и разделённым на слои: CLI, application, domain, infrastructure, presentation.

MVP включает локальную CLI-утилиту `docs-rag`, hybrid retrieval, OpenAI embeddings, индекс в `.docs-rag`, настраиваемые папки и OpenCode-команду `/docs`.

В MVP не входит:

- MCP-сервер;
- UI;
- web-сервис;
- поддержка нескольких embedding providers;
- распределённое хранение индекса;
- автоматическая публикация пакета;
- полноценный reranker поверх top-k результатов.

## Шаг 1. Исследование структуры проекта

Цель: определить, куда встроить CLI и как она должна запускаться в текущем репозитории.

Границы:

- изучить структуру проекта, package manager и существующие конфиги;
- проверить наличие OpenCode/command conventions;
- определить место для исходников CLI;
- не писать бизнес-логику RAG на этом шаге.

Выход:

- принятое решение о расположении CLI;
- список нужных npm-зависимостей;
- уточнённая структура директорий.

Критерии готовности:

- понятно, где лежит код CLI;
- понятно, как запускать CLI локально;
- нет изменений, не относящихся к подготовке структуры.

## Шаг 2. Каркас TypeScript CLI

Цель: создать минимальный исполняемый CLI-каркас `docs-rag`.

Границы:

- добавить TypeScript entrypoint;
- добавить команды-заглушки `init`, `index`, `query`, `status`;
- настроить сборку/запуск;
- добавить базовую обработку ошибок и exit codes;
- не подключать SQLite, OpenAI и реальную индексацию.

Выход:

- `docs-rag --help` работает;
- команды вызываются и возвращают контролируемый результат;
- CLI layer отделён от application layer.

Критерии готовности:

- CLI можно запустить из репозитория;
- команды не падают с необработанными исключениями;
- структура слоёв уже видна в коде.

## Шаг 3. Конфиг и init

Цель: реализовать создание и чтение `.docs-rag/config.json`.

Границы:

- реализовать `docs-rag init`;
- добавить config schema и валидацию;
- создать дефолтный конфиг с `folders`, `include`, `exclude`, `retrieval`, `embeddings`;
- проверять, что `OPENAI_API_KEY` не хранится в конфиге;
- не создавать индекс и не обходить документы.

Выход:

- `.docs-rag/config.json` создаётся при `init`;
- повторный `init` не затирает существующий конфиг без явного флага;
- ошибки конфига понятны пользователю.

Критерии готовности:

- невалидный конфиг приводит к понятной ошибке;
- дефолтный конфиг безопасен и исключает `.env`, `.git`, `.docs-rag`, `node_modules`;
- `OPENAI_API_KEY` читается только из окружения.

## Шаг 4. Поиск файлов и manifest

Цель: найти документы по include/exclude и подготовить manifest для incremental indexing.

Границы:

- реализовать обход папок из конфига;
- применить include/exclude patterns;
- вычислять `mtime`, размер и content hash;
- сохранять manifest в `.docs-rag/manifest.json` или SQLite;
- не выполнять чанкинг и embeddings.

Выход:

- CLI умеет определить добавленные, изменённые и удалённые документы;
- секретные и служебные файлы не попадают в список индексируемых.

Критерии готовности:

- `node_modules`, `.git`, `.docs-rag`, `.env*` исключены;
- повторный запуск корректно видит неизменённые файлы;
- удалённые файлы отражаются в manifest.

## Шаг 5. Markdown-aware chunking

Цель: разбивать документацию на осмысленные чанки по структуре Markdown.

Границы:

- реализовать domain-модель `Document` и `Chunk`;
- парсить Markdown-заголовки;
- сохранять `heading_path`;
- ограничивать размер чанка через `maxTokens`;
- добавлять overlap для больших секций;
- не писать чанки в SQLite и не считать embeddings.

Выход:

- из markdown-файла получается набор чанков с metadata;
- чанки пригодны для показа пользователю и для retrieval.

Критерии готовности:

- заголовки сохраняются в `heading_path`;
- большие секции режутся предсказуемо;
- пустые/мусорные чанки отбрасываются;
- логика чанкинга не зависит от CLI и SQLite.

## Шаг 6. SQLite storage и FTS

Цель: сохранить документы/чанки в SQLite и реализовать lexical search.

Границы:

- создать SQLite schema;
- добавить таблицы документов, чанков и FTS;
- реализовать upsert чанков;
- удалять чанки для удалённых файлов;
- реализовать BM25/FTS search;
- не добавлять OpenAI embeddings и hybrid ranker.

Выход:

- `docs-rag index` сохраняет чанки в `.docs-rag/index.sqlite`;
- lexical query возвращает релевантные чанки с file path и heading.

Критерии готовности:

- повторная индексация не создаёт дубли;
- удаление файла удаляет связанные чанки;
- FTS-результаты содержат score и metadata;
- storage layer не содержит presentation-форматирование.

## Шаг 7. OpenAI embeddings

Цель: добавить расчёт embeddings для чанков и запроса.

Границы:

- реализовать infrastructure adapter для OpenAI;
- читать `OPENAI_API_KEY` из env;
- сохранять embedding model и vector для чанков;
- не пересчитывать embeddings для неизменённых чанков;
- обработать rate limits и сетевые ошибки на базовом уровне;
- не реализовывать финальное hybrid ранжирование.

Выход:

- новые/изменённые чанки получают embeddings;
- query может получить embedding для пользовательского запроса.

Критерии готовности:

- без `OPENAI_API_KEY` пользователь получает понятную ошибку;
- неизменённые чанки не отправляются повторно в OpenAI;
- в индекс не попадают excluded files;
- ошибки OpenAI не выглядят как stacktrace без контекста.

## Шаг 8. Vector search

Цель: реализовать поиск по embedding similarity.

Границы:

- хранить vectors в SQLite или рядом с SQLite в `.docs-rag`;
- реализовать cosine similarity;
- вернуть top-k vector results;
- не смешивать vector score с lexical score в этом шаге.

Выход:

- vector search возвращает релевантные чанки по смысловой близости;
- результаты содержат score и metadata.

Критерии готовности:

- similarity считается детерминированно;
- отсутствующие embeddings корректно пропускаются;
- vector search не зависит от markdown/json presentation.

## Шаг 9. Hybrid ranker

Цель: объединить lexical и vector search в единый retrieval pipeline.

Границы:

- выполнить lexical search;
- выполнить vector search;
- нормализовать scores;
- объединить результаты по chunk id;
- применить веса `lexicalWeight` и `vectorWeight`;
- вернуть top-k финальных результатов;
- не форматировать ответ для OpenCode.

Выход:

- `docs-rag query` получает итоговый список `SearchResult`;
- результаты имеют общий `final_score`, source scores и metadata.

Критерии готовности:

- дубли чанков удаляются;
- веса берутся из конфига;
- пустые результаты обрабатываются явно;
- ranking logic находится в domain/application layer, не в CLI.

## Шаг 10. Presentation: markdown/json output

Цель: сформировать вывод, пригодный для OpenCode и для машинной обработки.

Границы:

- добавить `--format markdown`;
- добавить `--format json`;
- добавить `--max-chunks`;
- включать file path, heading, score и content;
- не менять retrieval logic.

Выход:

- Markdown-вывод можно напрямую подмешивать в prompt OpenCode;
- JSON-вывод пригоден для отладки и будущего MCP.

Критерии готовности:

- markdown содержит `Retrieved Documentation Context`;
- каждый источник имеет путь к файлу;
- при отсутствии результатов вывод явно сообщает, что контекст не найден;
- presentation layer не вызывает SQLite/OpenAI напрямую.

## Шаг 11. OpenCode-команда `/docs`

Цель: подключить CLI к OpenCode через slash-command.

Границы:

- создать команду `/docs` в подходящем месте;
- команда вызывает `docs-rag query "$ARGUMENTS" --format markdown --max-chunks 8`;
- команда инструктирует модель отвечать только по retrieved context;
- не добавлять MCP и отдельного агента.

Выход:

- пользователь может задавать вопросы через `/docs ...`;
- ответ содержит источники и не выполняет полный поиск по проекту без явной просьбы.

Критерии готовности:

- команда работает в OpenCode;
- в ответе есть ссылки на источники;
- если данных не хватает, модель говорит об этом явно.

## Шаг 12. Validation на `swarm-reports`

Цель: проверить end-to-end сценарий на реальной документации проекта.

Границы:

- настроить `folders` на `swarm-reports` или актуальный путь отчётов;
- выполнить `init`, `index`, `query`;
- проверить `/docs` на 2-3 вопросах;
- не расширять функциональность во время validation, кроме исправления найденных дефектов.

Выход:

- подтверждён рабочий flow от индексации до ответа OpenCode;
- найденные дефекты исправлены или зафиксированы.

Критерии готовности:

- индексация проходит без ошибок;
- query возвращает релевантные источники;
- OpenCode-ответ опирается на retrieved context;
- секретные файлы не индексируются.

## Шаг 14. Финальная проверка качества

Цель: убедиться, что MVP не превратился в монолитный скрипт и соответствует архитектурным ограничениям.

Границы:

- прогнать доступные тесты, typecheck и lint;

- проверить обработку ошибок;

Выход:

- MVP готов к использованию;
- технические долги явно зафиксированы.

Критерии готовности:

- typecheck проходит;
- тесты проходят или зафиксирована причина невозможности запуска;
- нет прямой зависимости CLI от SQLite/OpenAI;
- sensitive files исключены из индекса;
- отчёт обновлён по факту реализации.
