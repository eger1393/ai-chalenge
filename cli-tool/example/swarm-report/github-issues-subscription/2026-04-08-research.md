## Сводка консилиума

### 1. MCP → Backend: polling вместо webhook (единогласно)

**Проблема:** Спецификация предлагает webhook от MCP к backend, но:
- MCP протокол — request-response, server notifications только к подключённому клиенту
- github-explorer-mcp работает через supergateway (stdio→HTTP), нет механизма outgoing HTTP
- Webhook создаёт обратную зависимость MCP → Backend

**Решение:** Backend сам поллит MCP через существующий `McpToolRouter`:
- Новый MCP tool `check_new_issues(repository, since)` в github-explorer-mcp
- `SubscriptionPollerService` с `@Cron('*/5 * * * *')` на backend
- Подписки хранятся в PostgreSQL на стороне backend (не MCP)
- github-explorer-mcp остаётся stateless, без доступа к БД

### 2. Push-механизм: Persistent SSE (единогласно)

**Решение:** `GET /api/notifications/stream` — persistent SSE через `@Sse()` + rxjs Subject
- Проект уже использует SSE паттерн (use-pipeline.ts)
- Однонаправленный push — WebSocket избыточен
- Не требует новых портов/Docker-конфигурации
- EventSource автоматически переподключается
- JWT через query param или fetch-based SSE с Authorization header

### 3. Схема БД: отдельные таблицы (единогласно)

**НЕ расширять messages** — notification это другая сущность:
- `user_content TEXT NOT NULL` не подходит для системных уведомлений
- Pipeline не должен обрабатывать notifications

**Новые таблицы:**
```sql
issue_subscriptions (id, conversation_id FK, user_id FK, repository, last_checked_at, last_issue_number, expires_at, is_active, created_at)
issue_notifications (id, subscription_id FK, conversation_id FK, issue_number, issue_title, issue_url, issue_author, summary, is_read, created_at)
```

### 4. Backend модули

Два новых NestJS модуля:
- `subscription/` — CRUD подписок, polling, обработка новых issues
- `notification/` — SSE push, REST для mark-as-read, история

Новая зависимость: `@nestjs/schedule`

### 5. Frontend

**Компоненты:**
- `NotificationBubble` — визуальный блок уведомления в чате (teal палитра, Bell иконка)
- `SubscriptionIndicator` — панель подписок под ContextIndicator (progress bar TTL)
- `NotificationToast` — floating pill при новом уведомлении (если скроллнут вверх)

**Hooks:**
- `use-notification-stream` — persistent SSE соединение
- `use-subscriptions` — управление подписками
- `use-notifications` — коллекция уведомлений

**Context:** `NotificationProvider` на уровне app/layout.tsx

**Зависимости:** react-markdown + remark-gfm (для Markdown в уведомлениях)

### 6. UI/UX

- Цвет: teal (свободная палитра в проекте)
- TTL: progress bar + текстовый остаток (не countdown)
- Пустое состояние: индикатор не рендерится
- Истекшее: line-through + серый + скрывается через 10 мин
- Markdown: react-markdown + remark-gfm (нет рендерера в проекте)

## Расхождение

**Отображение уведомлений в чате:**
- Фронтенд-эксперт: уведомления НЕ в потоке messages (отдельный toast + drawer), т.к. подписки per-user, не per-conversation
- UI-дизайнер: уведомления в messages.map с проверкой типа, т.к. они привязаны к conversation

**Рекомендация:** Уведомления рендерить в потоке сообщений чата (привязаны к conversation_id), но как отдельный визуальный компонент NotificationBubble. Плюс toast при получении нового.
