# План: ollama-quantized-gemma-plan

- Дата: `2026-04-24 12:48`
- Статус: `План`

## Цель

Проверить, какая более квантованная локальная `Gemma` лучше подходит под текущий
`RTX 4090 24GB` на `superlook-gpu-dev`, чтобы по возможности полностью держать
веса модели на GPU, а затем при необходимости добавить выбранную модель как
доступный вариант в backend и frontend.

Кандидаты для проверки:

- `gemma4:31b-nvfp4`
- `gemma4:26b-nvfp4`

## Что уже известно

- На сервере сейчас установлена `gemma4:31b`.
- Текущая модель работает в `Q4_K_M`.
- `ollama ps` показывает частичный offload: `13%/87% CPU/GPU`.
- GPU сервера: `NVIDIA GeForce RTX 4090`, `24564 MiB` VRAM.
- `ollama` запущена как `systemd`-сервис `ollama.service`.
- В приложении локальная модель сейчас выбирается как `model` внутри провайдера
  `ollama`, а не как отдельный provider.

## План проверки

### 1. Зафиксировать baseline текущей модели

Собрать фактические метрики для текущей `gemma4:31b`:

- `nvidia-smi`
- `ollama list`
- `ollama ps`
- latency cold start
- latency warm start
- поведение на `num_ctx=8192`
- поведение на `num_ctx=16384`

Цель шага: понять, от чего именно отталкиваемся по CPU/GPU split, VRAM и
задержке ответа.

### 2. Установить кандидатов в Ollama

Скачать на `superlook-gpu-dev`:

- `gemma4:31b-nvfp4`
- `gemma4:26b-nvfp4`

После установки проверить:

- что теги появились в `ollama list`
- их фактический размер на диске
- что `ollama serve` работает штатно после pull

### 3. Прогнать runtime-smoke вне продукта

Для каждой модели выполнить короткие тесты через нативный `Ollama API`
`/api/chat`:

- обычный короткий текстовый ответ
- strict JSON-ответ с `think:false`
- тесты с `num_ctx=4096`
- тесты с `num_ctx=8192`
- тесты с `num_ctx=16384`

После каждого прогона фиксировать:

- `ollama ps`
- поле `PROCESSOR`
- поле `CONTEXT`
- usage VRAM через `nvidia-smi`
- стабильность ответа и отсутствие пустого `content`

### 4. Определить реальный full-GPU порог

Для каждой модели определить, при каком `num_ctx` она ещё целиком остаётся на
GPU.

Критерии:

- в `ollama ps` нет CPU-части или она исчезает до приемлемого нуля
- нет явного spill в CPU при стабильном тёплом прогоне
- нет деградации после прогрева модели

Цель шага: отличить "модель помещается в VRAM по весам" от реального рабочего
full-GPU режима с учётом KV cache и runtime overhead.

### 5. Сравнить качество и контрактность ответов

Для обеих моделей проверить 2-3 типовых продуктовых сценария:

- обычный чатовый ответ
- короткий structured JSON
- внутренний prompt уровня `rewrite` / `planning` / `validation`

Смотреть на:

- корректность формата
- пустой `content`
- лишнее reasoning
- мусорный JSON
- общую стабильность вывода

### 6. Проверить совместимость с текущим backend-контуром

Отдельно оценить поведение на двух путях:

- нативный `Ollama API` `/api/chat`
- OpenAI-compatible `/v1`

Это важно, потому что в текущем продукте:

- часть `ollama`-вызовов уже переведена на нативный `/api/chat`
- tool-aware execution всё ещё использует OpenAI-compatible поток `/v1`

### 7. Принять решение по продукту

Правило выбора:

- если `gemma4:31b-nvfp4` даёт полный GPU offload на нужном рабочем `num_ctx` и
  не ломает контракты, добавлять её как новый вариант модели
- если `gemma4:31b-nvfp4` всё ещё уходит в CPU, а `gemma4:26b-nvfp4` стабильно
  full-GPU, предпочтительнее добавить `26b-nvfp4`
- если обе модели спорны по стабильности или качеству, не менять продукт до
  дополнительного benchmark-раунда

## План продуктовых изменений после успешной проверки

### Backend

- добавить новый тег модели в `backend/src/ai/dto/ai-params.dto.ts`
- добавить metadata для модели:
  - pricing = `0`
  - practical context window
- убедиться, что `resolveAISelection()` принимает новый тег

### Frontend

- добавить модель в `frontend/src/types/ai-params.ts`
- добавить label для UI
- добавить корректный `MODEL_CONTEXT_SIZES`
- оставить `provider = "ollama"`, не создавать новый provider

### Validation

- `backend`: `npm run build`
- `frontend`: `npm run build`
- живой smoke-test через UI

## Предварительная оценка

- Самый безопасный кандидат на full-GPU: `gemma4:26b-nvfp4`
- Самый желанный кандидат по качеству: `gemma4:31b-nvfp4`
- Для `31b-nvfp4` нельзя обещать полный GPU offload без живой проверки на
  рабочем `num_ctx`

## Ограничения плана

- Проверки ещё не запускались в рамках этого документа.
- Это именно план работ, а не отчёт по фактической валидации.
- Итоговое решение должно приниматься только после runtime-замеров на сервере.
