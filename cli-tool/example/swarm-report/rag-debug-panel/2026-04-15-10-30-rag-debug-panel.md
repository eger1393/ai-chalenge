# Отчёт по задаче: RAG в debug-панели

## Статус

Готово

## Краткое описание задачи

Добавить отдельные debug-данные по RAG и отобразить их во frontend debug-панели аналогично MCP tool calls, без хранения полного текста найденных сообщений внутри debug-записи.

## Что выполнено

- В `message_debug` добавлено поле `rag_context JSONB`
- При завершении обработки сообщения backend сохраняет в `rag_context` только компактные ссылки на найденные чанки:
  - `enabled`
  - `matchCount`
  - `chunkId`
  - `documentId`
  - `similarity`
  - `rank`
- `GET /api/messages/:id/debug` обогащает RAG-ссылки данными из `rag_chunks` и `rag_documents`
- Во frontend debug-панели добавлена отдельная вкладка `RAG`
- Вкладка показывает:
  - состояние RAG
  - количество найденных фрагментов
  - релевантность
  - ID сообщения и чанка
  - дату и источник
  - раскрываемый текст чанка
  - раскрываемый полный текст исходного сообщения

## Проверки

- Локально:
  - `backend`: `npm run build` — успешно
  - `frontend`: `npm run build` — успешно
- Stage:
  - `docker compose up -d --build backend frontend` — успешно
  - backend стартовал, миграции прошли
  - frontend отвечает на `http://167.235.226.104:6501`
  - backend отвечает на `http://167.235.226.104:6500/api/auth/me` ожидаемым `401` без токена
  - `message_debug.rag_context` существует как `jsonb`
  - SQL-запрос обогащения `chunkId -> rag_chunks -> rag_documents` возвращает текст сообщения и метаданные чанка

## Ограничения и допущения

- Для старых сообщений, обработанных до появления `rag_context`, отдельная вкладка RAG появится только после новой обработки сообщения
- В debug-записи хранится только ссылка на чанк, поэтому при удалении или полной переиндексации RAG-таблиц старые debug-записи могут показать, что чанк уже не найден
