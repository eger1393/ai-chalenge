# Отчёт по задаче: RAG всегда отвечает и явно показывает покрытие

## Краткое описание задачи

Нужно было изменить текущую реализацию RAG-режима так, чтобы ассистент больше не прекращал ответ при недостаточном покрытии retrieval, всегда выводил ссылки на данные из RAG, а при отсутствии доказательств явно помечал это в ответе. Дополнительно требовалось проверить связку RAG с контекстными стратегиями, в первую очередь со стратегией `Факты`.

## Что реализовано

- Убран продуктовый контракт `INSUFFICIENT -> REFUSE` в strict RAG:
  - planning и execution теперь ориентированы на ответ по существу даже при неполном покрытии retrieval
  - финальный strict RAG-ответ всегда нормализуется в разделы `Краткий ответ`, `Статус RAG`, `Источники из RAG`
  - при отсутствии ссылок в финальном ответе выводится явная пометка `Данные в RAG отсутствуют`
- Усилен backend-контроль strict RAG:
  - planning с legacy `REFUSE` теперь отвергается и при возможности автоматически ремонтируется через `policy_repair`
  - execution обязан возвращать `ragNotice` со статусом `GROUNDED` / `PARTIAL` / `ABSENT`
  - ссылки валидируются против выбранных `chunk_id`
- Доведена стратегия контекста до RAG end-to-end:
  - `contextStrategy` передаётся при создании диалога
  - `contextStrategy` применяется при отправке сообщения
  - `GET /conversations/:id` возвращает фактическую стратегию контекста диалога
  - `updateStrategy` больше не затирает `strategy_data`, если при смене стратегии не переданы новые данные
- Добавлен retrieval hint от стратегии контекста:
  - для `sticky_facts` используется снимок facts
  - для `sliding_window` и `branching` используется компактный хвост диалога
  - hint участвует в query rewrite / retrieval только для снятия неоднозначности и не считается доказательством
- Обновлена debug-наблюдаемость:
  - в `message_debug.rag_context` сохраняется retrieval hint
  - в `strategy_metadata.ragPipeline` сохраняются `ragStatus` и `ragNotice`
  - debug-panel теперь показывает pipeline и стратегию контекста одновременно
- Исправлен сопутствующий дефект в `sendMessage`:
  - проверка владения диалогом теперь выполняется до изменения параметров и стратегии контекста

Все перечисленные проверки завершились успешно.

## Ограничения и допущения

- Живой сценарий с реальным retrieval по базе и фактическим LLM-ответом в этом проходе не воспроизводился; валидация выполнена на уровне кода, типов и production-сборки
- Legacy-парсинг `REFUSE` в strict RAG сохранён только как защитная совместимость для repair/диагностики, но целевой контракт ответа теперь всегда `ANSWER`
