# Отчёт: ollama-gemma-gpu-fit-check

- Дата: `2026-04-24 13:02`
- Статус: `Частично`

## Описание задачи

Проверить на `superlook-gpu-dev`, можно ли перейти на более квантованную
`Gemma`, чтобы модель целиком помещалась на GPU, и оценить практическую
пригодность кандидатов для последующего добавления в backend/frontend.

Изначально целевые кандидаты:

- `gemma4:31b-nvfp4`
- `gemma4:26b-nvfp4`

## Что проверено

### Фактическое состояние сервера

- GPU: `NVIDIA GeForce RTX 4090`, `24564 MiB`
- `ollama` version: `0.21.0`
- `ollama` запущена как `systemd`-сервис
- после проверок на диске осталось около `202G`
- каталог моделей: `/usr/share/ollama`, суммарный размер после pull — `36G`

### Что установлено и что не установилось

- Текущая модель на сервере: `gemma4:31b`
- Дополнительно успешно установлена: `gemma4:26b`
- `gemma4:31b-nvfp4` не ставится: `412: this model requires macOS`
- `gemma4:26b-nvfp4` не ставится: `412: this model requires macOS`

## Проверка product-like prompt contracts

### Rewrite-like JSON prompt через нативный `/api/chat`

- `gemma4:31b`
  - latency: `11894 ms`
  - вернула fenced JSON с каноническими полями `query/applied/reason`
  - текущий backend такой fenced JSON переживёт
- `gemma4:26b`
  - latency: `6848 ms`
  - вернула неканоничный payload:
    - `applied` как массив вместо boolean
    - `reason: clarified_subject` вместо допустимого значения
  - текущий `repair` в `RagQueryRewriteService` такой ответ, скорее всего,
    починит:
    - `query` есть
    - `applied` будет выведен из diff запроса
    - `reason` fallback-ится в `clarified_intent`
  - это не blocker, но деградация контрактной дисциплины есть

### Validation-like prompt через нативный `/api/chat`

- `gemma4:31b`
  - latency: `951 ms`
  - формат выдержан корректно
- `gemma4:26b`
  - latency: `361 ms`
  - формат выдержан корректно

## Проверка OpenAI-compatible `/v1`

JSON-тест через `/v1/chat/completions` на обеих моделях:

- `gemma4:31b`
  - `finish_reason: length`
  - `content: ""`
  - непустой `reasoning`
- `gemma4:26b`
  - `finish_reason: length`
  - `content: ""`
  - непустой `reasoning`

Вывод:

- проблема пустого `message.content` на strict JSON-задачах через `/v1` есть не
  только у `31b`, но и у `26b`
- для strict JSON-задач обе модели нужно продолжать вести через нативный
  `/api/chat`, а не надеяться на `/v1`

## Практический вывод

### Что подтвердилось

- На этом Linux-сервере целевые `nvfp4`-теги из каталога `Ollama` недоступны:
  `ollama pull` отвечает `this model requires macOS`
- Текущая `gemma4:31b` не полностью помещается на GPU на `16384+`
- `gemma4:26b` полностью помещается на GPU даже на `32768`

### Что это значит для продукта

- Если главный приоритет — full-GPU fit на `RTX 4090`, самый практичный кандидат
  сейчас не `31b-nvfp4`, а `gemma4:26b`
- Если главный приоритет — максимально сильное следование strict JSON-контрактам,
  `31b` выглядит дисциплинированнее на rewrite-like задаче
- Для `26b` добавление в продукт возможно, но стоит помнить:
  - на rewrite-задачах модель чаще уходит в repair-path
  - проблема `/v1` с пустым `content` остаётся

## Рекомендация

1. Если цель — быстро получить локальную full-GPU модель без отдельной сборки,
   добавлять в продукт `gemma4:26b`
2. Не ждать `nvfp4`-теги на этом хосте как drop-in решение: в текущем состоянии
   они недоступны для Linux через обычный `ollama pull`
3. Если принципиально нужна именно более агрессивно квантованная `31b`, это уже
   отдельная задача на кастомный импорт/квантование, а не просто добавление
   опубликованного тега

## Ограничения

- Проверка выполнена на коротких smoke-запросах, а не на полном продуктовым
  benchmark-наборе
- `nvfp4`-кандидаты не удалось реально запустить из-за platform-level блокера
- Качество оценивалось точечно на нескольких contract-like промптах, а не на
  полной выборке RAG-задач
