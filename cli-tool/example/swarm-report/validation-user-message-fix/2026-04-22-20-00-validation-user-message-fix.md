# Отчёт: validation-user-message-fix

- Дата: `2026-04-22 20:00`
- Статус: `Исправлен`

## Описание проблемы

Шаг `validation` периодически отвечал по существу исходного пользовательского вопроса вместо формата `VERDICT/SCORE/REASON/ISSUES`. Во фронтенде это проявлялось как отказ с причиной `Валидация не вернула обязательный формат VERDICT/SCORE/REASON/ISSUES`.

## Корневая причина

- В `buildValidationMessages()` для `standard` и `rag` стратегий в конец диалога передавался `userMessage = params.userContent`, то есть исходный запрос пользователя.
- Для модели это был последний и самый свежий пользовательский сигнал, поэтому она нередко отвечала именно на вопрос пользователя, а не выполняла роль валидатора.
- Fallback-парсер в `StepRunnerService.parseValidation()` не умел извлекать полезную причину из свободного списка проблем и сводил всё к общей ошибке формата.

## Что исправлено

- В `standard-message-processing.strategy.ts` validation теперь получает отдельный user prompt с явной инструкцией проверять plan/execution и не отвечать на исходный вопрос.
- В `rag-message-processing.strategy.ts` сделано то же самое для строгого RAG validation.
- В системные validation prompt добавлен явный запрет отвечать пользователю по существу запроса.
- В `step-runner.service.ts` добавлен fallback для свободного списка проблем: если модель всё же вернула осмысленный issue-list вместо строгого формата, backend извлекает из него reason и помечает validation как fail с содержательной причиной.

## Результаты проверки

- Выполнено: `npm run build` в `backend/`
- Результат: успешно

## Ограничения

- Полный runtime smoke-test validation шага не запускался в рамках этого запроса.
- Fallback остаётся fail-safe: свободный текст не приводит к `PASS`, а только превращается в осмысленный `FAIL` вместо общей ошибки формата.
