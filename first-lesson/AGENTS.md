# Global Profile

## Карта проекта

Архитектура, модули, файлы, потоки данных и действующие контрактные документы
описаны в **[PROJECT_MAP.md](./PROJECT_MAP.md)**.
Перед началом работы над задачей сначала прочитать этот файл.

## Персонализация

- Язык общения: русский
- Имею право не соглашаться с решениями пользователя, если они ведут к
  костылю, дыре в безопасности, скрытой поломке или лишнему техдолгу
- Качество и безопасность важнее скорости
- Долгосрочная польза важнее быстрого, но хрупкого результата
- Если пользователь настаивает на рискованном решении, риски нужно назвать
  явно и зафиксировать в отчёте
  
  
## Режим работы

### Разделение уровней

В работе есть два разных уровня режима:

- системный режим среды
- проектный режим работы

Системный режим среды задаётся внешними инструкциями и не переключается через
этот файл.

Проектный режим работы агент определяет сам по запросу пользователя и контексту
задачи.

### Проектные режимы

- `Планирование`
- `Исполнение`

### Автодетект проектного режима

Используй `Планирование`, если пользователь:

- просит составить план
- хочет декомпозицию на этапы или задачи
- просит продумать архитектуру, контракт, схему, API или модель данных
- хочет сравнить варианты
- ещё не дал достаточно данных для безопасной реализации

Используй `Исполнение`, если пользователь:

- явно просит реализовать, изменить, исправить, создать, удалить или обновить
- просит подключиться, проверить, запустить, провалидировать или собрать
- ожидает фактический результат в файлах, коде, документации или командах
- дал достаточно контекста, чтобы можно было выполнить задачу без отдельного
  проектирования

### Правило по умолчанию

Если запрос двусмысленный:

- для новой фичи, архитектуры, контрактов и схем сначала выбирай
  `Планирование`
- для локальной, конкретной и технически однозначной задачи выбирай
  `Исполнение`

### Приоритет системного режима

- если системная среда запрещает изменения, агент ограничивается планированием
  и не редактирует файлы
- если системная среда допускает изменения, агент сам выбирает между
  `Планированием` и `Исполнением` по правилам выше
- пользователь не обязан вручную переключать режим перед каждой задачей

## Выбор профиля

Каждый запрос обрабатывается в рамках одного профиля:

- `Фича`
- `Баг`

### Автодетект профиля

- Баг, ошибка, краш, не работает, ломается, исключение, трассировка стека,
  `stacktrace`, `NPE`, `500`, регрессия, `regression` → `Баг`
- Фича, добавить, реализовать, новый экран, интеграция, API-эндпоинт →
  `Фича`

Если пользователь явно указал профиль, использовать его.

Если профиль неочевиден и от него меняется процесс работы, задать короткий
уточняющий вопрос обычным сообщением.

Профиль и режим работы — это разные вещи:

- `Фича` может идти через `Планирование` или через `Исполнение`
- `Баг` может идти через диагностику без изменений или через полный цикл
  исправления

## Общие правила работы

### Последовательность

Агент всегда определяет работу в таком порядке:

1. профиль задачи
2. проектный режим работы
3. текущую стадию процесса

### Исследование перед вопросами

- Сначала нужно собрать факты из файлов, конфигурации и действующей
  документации
- Не задавай пользователю вопросы, на которые можно ответить чтением
  репозитория или запуском неразрушающих команд
- Если вопрос всё же нужен, он должен существенно менять план или реализацию

### Стадии и коммуникация

- Перед началом существенной работы сообщай текущую стадию и следующую стадию
- Для длинных задач явно проходи стадии процесса
- Для маленьких и однозначных задач стадии можно проходить компактно, но не
  пропускать логически

### Доступные инструменты

- Используй только реально доступные в среде инструменты
- Не завязывай процесс на несуществующие или недоступные инструменты, внешние
  обязательные субагенты или внешние агентные платформы
- Если в среде доступны субагенты, их можно использовать как опциональное
  ускорение, но не как обязательную часть процесса

### Работа с чужими изменениями

- Не откатывай чужие изменения без явного запроса пользователя
- Если в дереве есть неожиданные правки, сначала пойми, мешают ли они задаче
- Если они не мешают, работай поверх них

### Актуализация карты проекта

Если задача добавила новые устойчивые сущности, обнови `PROJECT_MAP.md`.

Обновлять `PROJECT_MAP.md` нужно, если появились:

- новые каталоги с проектной ролью
- новые канонические документы
- новые таблицы или важные схемы
- новые env-переменные
- новые точки входа в основной процесс

### Отчёты

По завершённой задаче сохраняй отчёт в:

```text
./swarm-report/<slug>/<YYYY-MM-DD-HH-MM>-<slug>.md
```

Если задача завершена частично, это нужно явно указать в отчёте.

## Validation

Валидация зависит от фактической поверхности задачи.

### Если изменялся код

- запусти релевантные тесты
- запусти релевантную сборку
- проверь, что нет очевидных ошибок типов, импорта и исполнения

### Если изменялись shell-скрипты или навыки

- используй `bash -n`
- используй `quick_validate.py`, если задача касается структуры навыка
- используй проверочный запуск, если он безопасен и не меняет данные

### Если изменялись документы и контракты

- перечитай изменённые файлы целиком
- проверь ссылки, внутреннюю согласованность и отсутствие противоречий с
  каноническими документами планирования
- проверь, что документ не оставляет незафиксированных решений уровня
  “определим потом”

### Если полноценного серверного и клиентского кода нет

- не имитируй несуществующую сборку
- валидируй документальную, контрактную и скриптовую согласованность

## Профиль: Фича

### Целевой стек

Этот стек применять только если задача реально касается реализации Watch RAG
или если в репозитории появятся соответствующие модули.

#### Backend

- Node.js + TypeScript
- Nest.js
- PostgreSQL
- SQL без ORM-диалектов

#### Frontend

- React + TypeScript

### Стадии

1. `Research`
2. `Plan`
3. `Executing`
4. `Validation`
5. `Report`
6. `Done`

### Правила прохождения стадий

- `Research` — собрать факты, изучить кодовую базу и действующие документы
- `Plan` — зафиксировать план, если задача нетривиальная, архитектурная,
  неоднозначная или пользователь явно хочет план
- `Executing` — выполнить задачу end-to-end, если системный режим допускает
  изменения и контекст уже достаточен
- `Validation` — проверить результат по реальной поверхности задачи
- `Report` — сохранить итоговый отчёт и зафиксировать ограничения

### Когда можно не останавливаться на Plan

Если задача локальная, однозначная и системный режим допускает изменения,
после краткого `Research` можно сразу перейти к `Executing`, затем к
`Validation` и `Report` в рамках того же запроса.

### Что обязательно должно быть в отчёте по фиче

- краткое описание задачи
- что именно реализовано
- результаты проверки
- ограничения и допущения
- статус: `Готово` или `Частично`

## Профиль: Баг

### Целевой стек

Если баг относится к будущим модулям Watch RAG, использовать тот же стек:

- Node.js + TypeScript
- Nest.js
- PostgreSQL
- React + TypeScript

### Стадии

1. `Reproduce`
2. `Diagnose`
3. `Fix`
4. `Validation`
5. `Report`
6. `Done`

### Правила прохождения стадий

- `Reproduce` — воспроизвести баг и зафиксировать симптомы
- `Diagnose` — определить корневую причину
- `Fix` — внести минимальное, но надёжное исправление
- `Validation` — проверить, что баг устранён и нет явной регрессии
- `Report` — сохранить итоговый отчёт

### Если баг не воспроизводится

- сделай несколько разумных попыток воспроизведения
- зафиксируй, что уже проверено
- задай короткий уточняющий вопрос, только если без него нельзя двигаться
- если данных всё равно недостаточно, оформи частичный отчёт со статусом
  `Не воспроизводится` или `Частично`

### Что обязательно должно быть в отчёте по багу

- описание проблемы
- шаги воспроизведения или факт их отсутствия
- корневая причина, если найдена
- что исправлено
- результаты проверки
- статус: `Исправлен`, `Не воспроизводится` или `Частично`
