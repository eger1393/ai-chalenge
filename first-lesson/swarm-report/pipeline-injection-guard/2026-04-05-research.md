## Сводка консилиума

### Архитектор

- **Рекомендация:** Выделить `PipelineGuardService` в отдельный файл `pipeline-guard.service.ts` (SRP, pipeline.service.ts уже ~935 строк)
- **Точки вызова:** санитайзер ДО создания pipeline_run; PIPELINE SECURITY блок в build*Messages; INJECTION verdict в parseValidation; final gate перед записью completed
- **Риски:** дублирование логики между `runPipeline` и `resumePipeline` — guard-проверки нужны в обоих; при resume инварианты загружаются заново — нужна повторная фильтрация
- **БД:** новых статусов не нужно, используем `failed` + `error_message`
- **Final gate обязателен** — SQL-проверка 3 completed steps

### Фронтенд-эксперт

- **Типы:** расширить PipelineStatus на `'injection_blocked'`, добавить `injectionBlock?` в PipelineRunState
- **Хук:** два новых case в handleEvent — `injection_blocked` (терминальный) и `injection_detected` (информационный на шаге)
- **Stepper:** новое состояние в getStepState, иконка ShieldAlert
- **Bubble:** alert-блок аналогичный error, но amber-цвет
- **Controls:** injection_blocked рядом с failed — нельзя resume/pause

### UI-дизайнер

- **Иконка:** `ShieldAlert` из lucide-react
- **Цвет:** amber (оранжевый), НЕ красный — красный занят failed
- **Классы:** `text-amber-500` иконка, `text-amber-600` лейбл, `bg-amber-400` коннектор
- **Анимация:** однократный pulse (3 цикла)
- **Bubble:** `bg-amber-50 border-amber-200`, текст amber-700

### API-дизайнер

- **Формат:** новые события вписываются в текущий SSE discriminated union
- **injection_blocked:** отправляется ВМЕСТО pipeline_started (pipeline_run не создаётся), НЕ содержит pipelineId
- **Порядок:** saveUserMessage → sanitizerCheck → [blocked? → emit injection_blocked + save assistant reply + end] → createPipelineRun → emit pipeline_started
- **Конверсационный fallback:** ДА — при блокировке сохранить assistant message с объяснением
- **injection_detected:** возникает на шаге validation, аналогично validation_failed
