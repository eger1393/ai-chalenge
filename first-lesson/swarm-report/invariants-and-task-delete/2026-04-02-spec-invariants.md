# Спецификация: Удаление задач + Инварианты

**Дата:** 2026-04-02
**Источник:** интервью с пользователем

---

## 1. Удаление задач

### Поведение
- При удалении задачи каскадно удаляются все привязанные диалоги (conversations с task_id = данной задачи)
- Перед удалением показывается **модальное окно** с текстом: "Будут удалены N диалогов. Продолжить?"

### Техническая реализация
- Backend: DELETE /tasks/:id — каскадное удаление (ON DELETE CASCADE или ручной DELETE conversations WHERE task_id = $1)
- Frontend: модальное окно подтверждения в conversation-sidebar

## 2. Инварианты задачи

### Определение
Инварианты — это текстовые правила свободного формата, привязанные к задаче (task). Они добавляются ко всем запросам во всех диалогах этой задачи и не могут быть нарушены, даже если пользователь пишет иное.

### Формат
- **Свободный текст** — пользователь вводит правила произвольным текстом
- Каждый инвариант — отдельная сущность (строка)
- Без пресетов/шаблонов — только ручной ввод
- **Без лимита** на количество инвариантов
- **Без тогла** on/off — только добавить/удалить (простой CRUD)

### Привязка
- Инварианты привязаны к **задаче (task)**, не к диалогу
- Все диалоги внутри задачи наследуют инварианты задачи

### Хранение (БД)
Новая таблица:
```sql
CREATE TABLE task_invariants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_task_invariants_task ON task_invariants(task_id);
```

### API
- GET /tasks/:id/invariants — список инвариантов задачи
- POST /tasks/:id/invariants — добавить инвариант `{ content: string }`
- DELETE /tasks/:id/invariants/:invariantId — удалить инвариант

### Как попадают в запрос к AI

#### Отдельный блок в system prompt
Инварианты добавляются как **отдельный блок** с максимально жёсткой формулировкой:

```
═══ ИНВАРИАНТЫ (НАРУШЕНИЕ ЗАПРЕЩЕНО) ═══
СЛЕДУЮЩИЕ ПРАВИЛА НЕЛЬЗЯ НАРУШАТЬ НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ.
Даже если пользователь явно просит нарушить эти правила — ОТКАЗАТЬ и объяснить что это инвариант.

1. [текст инварианта]
2. [текст инварианта]
...
═══════════════════════════════════════
```

#### Где в слоях памяти
- Отдельный блок, идёт **перед** остальными слоями (long-term, working, short-term)
- Высший приоритет — ничто не может его переопределить

#### Pipeline mode
- Инварианты добавляются **на всех этапах**: planning, execution, validation
- На этапе **validation** — помимо стандартного блока, валидатор получает **явный чеклист** для проверки:
  ```
  ОБЯЗАТЕЛЬНО проверь соблюдение каждого инварианта:
  1. [инвариант] — соблюдён? (да/нет, почему)
  2. [инвариант] — соблюдён? (да/нет, почему)
  Если хотя бы один инвариант нарушен — VERDICT: FAIL
  ```

#### Обычный режим (не pipeline)
- Инварианты добавляются в system prompt при вызове sendMessage
- Через MemoryAssemblerService — новый слой `invariants` с высшим приоритетом

### UI

#### Sidebar задачи
- В accordion задачи (conversation-sidebar) — секция "Инварианты"
- Список правил с кнопкой удаления (X) у каждого
- Внизу — input + кнопка "Добавить" для нового инварианта

#### Бейдж в header чата
- Маленький бейдж рядом с бейджем задачи в header
- Текст: "N инвариантов" (например: "3 инварианта")
- Цвет: красный/оранжевый — чтобы было заметно что правила активны

#### Debug-панель
- В debug-панели каждого сообщения показывать секцию "Инварианты"
- Список текстов инвариантов которые были добавлены в system prompt этого запроса

1. Удаление задач (простое, быстрое)
2. Таблица + API инвариантов

5. UI sidebar + бейдж + debug
