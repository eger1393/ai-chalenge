# Отчёт: local-model-optimization-plan

- Дата: `2026-04-22 20:29`
- Статус: `Готово`

## Краткое описание задачи

Подготовить практический план оптимизации локальной модели под текущий продуктовый контур: подобрать runtime-параметры, оценить роль квантования и предложить более точные prompt-шаблоны.

## Что проверено фактически

### На `superlook-gpu-dev`

- Установлена модель: `gemma4:31b`
- Квантование установленной модели: `Q4_K_M`
- Архитектурный context length модели: `262144`
- Дефолты model-level параметров:
  - `temperature = 1`
  - `top_k = 64`
  - `top_p = 0.95`
- По ранее зафиксированному рабочему запуску на этой `RTX 4090 24GB` практический runtime context был `32768`
- Сейчас на сервере загруженных моделей в памяти нет (`ollama ps` пустой)

### Практический вывод по железу

- На одной `RTX 4090 24GB` `gemma4:31b` уже работает близко к потолку по VRAM.
- Значит оптимизация должна в первую очередь идти не в сторону “максимум всего”, а в сторону более узких профилей под конкретные типы задач.

## Что можно сделать

### 1. Разделить профиль параметров по типу задачи

Одна и та же конфигурация не подходит одновременно для:

- обычного чата
- RAG answer
- strict JSON-задач
- planning/validation

Рекомендуемые стартовые профили:

| Сценарий | temperature | num_predict / max tokens | num_ctx | think | Комментарий |
| --- | --- | --- | --- | --- | --- |
| Query rewrite / JSON extraction | `0` | `96-192` | `2048-4096` | `false` | Нужна детерминированность, короткий вывод |
| Validation / classifier-like checks | `0` | `64-160` | `2048-4096` | `false` | Нельзя давать модели “болтать” |
| Planning | `0.1-0.2` | `512-1200` | `4096-8192` | `false` | Нужна вариативность, но без расползания |
| RAG execution | `0.2-0.4` | `700-1800` | `8192-16384` | `false` | Баланс между точностью и связностью |
| Обычный разговорный чат | `0.4-0.7` | `512-1500` | `4096-8192` | по необходимости | Только если нужен более “живой” стиль |

### 2. Не использовать дефолт `temperature=1` как универсальный режим

Текущий model-level default `temperature=1` слишком высокий для большинства продуктовых задач backend.

Это особенно плохо для:

- structured JSON
- validation
- rewrite
- коротких factual RAG-ответов

Практический вывод:

- Для backend-пайплайна надо почти всегда задавать `temperature` явно в запросе.
- Для strict-stage задач `0` или `0.1` лучше дефолта модели.

### 3. Ограничить context window под задачу, а не тянуть максимум

Хотя модель архитектурно поддерживает `262144`, реальный рабочий контур на текущем железе уже зафиксирован как `32768`, и длинный контекст быстро съедает VRAM через KV cache.

Рекомендации:

- Для коротких внутренних задач (`rewrite`, `validation`, классификация) держать `num_ctx` маленьким: `2k-4k`
- Для planning и обычного RAG не поднимать без необходимости выше `8k-16k`
- `32k` использовать только когда есть реальная потребность и измеренный выигрыш

Практический эффект:

- ниже latency
- меньше риск reload / memory pressure
- меньше стоимость по времени на prefill

### 4. Держать `num_predict` коротким для внутренних стадий

Многие внутренние ошибки появляются потому, что модели дают слишком много “права говорить”.

Рекомендации:

- `rewrite`: `96-128`
- `validation`: `64-128`
- classification / route-selection: `32-96`
- JSON extraction: `96-192`

Если модель начинает писать длинные рассуждения, это почти всегда сигнал, что лимит для конкретной stage-задачи слишком щедрый или prompt слишком общий.

### 5. Для strict JSON-задач использовать нативный `/api/chat`

Для вашего контура это особенно важно.

Уже подтверждено практикой:

- OpenAI-совместимый `/v1/chat/completions` на `gemma4:31b` может тратить completion на `reasoning` и оставлять пустой `message.content`
- нативный `/api/chat` лучше подходит для `think:false` и `format:"json"`

Рекомендация:

- для `rewrite`, `validation`, extraction и прочих строгих внутренних шагов использовать именно `/api/chat`
- передавать `think:false`
- для JSON-задач передавать `format:"json"` или JSON Schema

### 6. Привести prompt-шаблоны к task-specific контрактам

Главная ошибка локальных моделей в прод-пайплайнах — слишком общие промпты.

Для `gemma4:31b` лучше работают шаблоны, где:

- роль узкая и одна
- формат ответа задан буквально
- есть запрет на markdown / пояснения / пересказ
- первая строка и структура ответа жёстко фиксированы
- есть 1-3 примера нужного формата

#### Пример для strict validation

Не так:

- “Проведи строгую проверку и оцени качество ответа”

Лучше:

```text
Ты выполняешь только validation.
Не отвечай на вопрос пользователя.
Не пересказывай входные данные.
Первая строка должна начинаться с VERDICT:
Формат ответа ровно такой:
VERDICT: PASS | FAIL | INJECTION
SCORE: <1-10>
REASON: <одна короткая причина>
ISSUES: <краткий список>
```

#### Пример для rewrite

```text
Ты переписываешь запрос только для retrieval.
Не отвечай на вопрос.
Не добавляй новые факты.
Верни только JSON.
Если запрос уже хороший, не улучшай его ради улучшения.
```

#### Пример для RAG answer

```text
Используй RAG как основной источник.
Если данных не хватает, явно пометь неполное покрытие.
Не выдавай непроверенные детали за подтвержденный факт.
Цитаты должны быть короткими и дословными.
```

### 7. Квантование: что реально можно сделать

Сейчас на сервере уже используется квантованная модель `Q4_K_M`.

Это значит:

- квантование уже не “следующий шаг”, а текущее состояние
- выигрывать дальше можно только сравнением с другими вариантами модели, если они реально доступны

Что имеет смысл проверить:

1. Оставить `Q4_K_M` как baseline качества
2. Если нужна меньшая latency и ниже VRAM pressure:
   - попробовать более агрессивную квантизацию той же модели, если она доступна в Ollama/gguf-каталоге
   - либо попробовать меньшую модель того же семейства
3. Если нужен максимум качества для planning/execution, а latency вторична:
   - оставить `Q4_K_M`, но оптимизировать `num_ctx`, `num_predict`, prompt и `think:false`

Важно:

- Через обычный `Modelfile` нельзя “магически переквантовать” уже готовый blob в новый GGUF-класс.
- Для реального эксперимента с квантизацией нужен либо другой опубликованный тег модели, либо отдельная сборка/импорт другого GGUF.

### 8. Добавить измеримый benchmark вместо субъективного тюнинга

Без этого оптимизация будет “на глаз”.

Минимальный benchmark-пакет для вашей задачи:

- 20 запросов на rewrite
- 20 запросов на validation
- 20 RAG-вопросов с ожидаемым grounded answer
- 10 ambiguous / insufficient кейсов

Собирать по каждому прогону:

- latency p50/p95
- долю валидного JSON
- долю пустых / malformed ответов
- долю лишних рассуждений / markdown
- долю pass/fail по вашему внутреннему контракту
- число cold start и reload, если заметны по логам

## Рекомендуемый практический план

### Шаг 1. Ввести 3 отдельные runtime-конфигурации

- `strict_json`
- `rag_answer`
- `general_chat`

### Шаг 2. Для backend internal stages использовать только `strict_json`

- `temperature=0`
- `num_predict=96-128`
- `num_ctx=2048-4096`
- `think=false`
- нативный `/api/chat`

### Шаг 3. Для RAG execution ввести отдельный профиль

- `temperature=0.2-0.3`
- `num_predict=900-1400`
- `num_ctx=8192-16384`
- `think=false`

### Шаг 4. Зафиксировать prompt templates по сценарию

- отдельный prompt для rewrite
- отдельный prompt для validation
- отдельный prompt для grounded RAG answer

### Шаг 5. Только после этого сравнивать квантование

Иначе будет непонятно, что дало эффект: quantization или просто нормальный prompt/params.

## Главный вывод

Для текущего `dev-gpu` контура основной резерв улучшения не в “ещё одной магической модели”, а в трёх вещах:

- убрать универсальные дефолты и ввести task-specific runtime profiles
- использовать нативный `/api/chat` для strict JSON-задач
- сузить prompt-шаблоны под конкретные stage-контракты

Квантование у вас уже есть (`Q4_K_M`), поэтому следующий шаг — не “включить квантование”, а осознанно сравнить текущий baseline с альтернативным quant/size-вариантом, если он реально доступен.
