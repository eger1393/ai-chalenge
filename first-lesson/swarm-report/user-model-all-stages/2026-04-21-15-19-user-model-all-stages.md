# Отчёт: user-model-all-stages

## Задача

Убрать хардкод моделей в backend и сделать так, чтобы для пользовательского контура использовались `provider/model`, выбранные пользователем, а не отдельные фиксированные GPT-модели для внутренних шагов.

## Что реализовано

- `planning` и `validation` в pipeline больше не используют фиксированные internal GPT-модели.
- `planning`, `execution` и `validation` теперь идут через `provider/model` выбранного диалога.
- RAG `query rewrite` больше не использует отдельную захардкоженную модель и теперь вызывается через выбранные пользователем `provider/model`.
- `sticky_facts` extraction больше не использует фиксированную модель и теперь вызывается через выбранные пользователем `provider/model`.
- Summary для `subscription callback` больше не использует фиксированную модель и теперь берёт `provider/model` из связанного диалога по `conversation_id`.
- Из `backend/src/rag/constants.ts` убран хардкод `RAG_QUERY_REWRITE_MODEL`.
- В schema migration дефолтные `provider/model` для `conversations` теперь берутся из общего AI-каталога, а не из строкового literal внутри SQL.

## Проверки

- `backend`: `npm run build` — успешно

## Ограничения и допущения

- Каталог допустимых моделей по-прежнему остаётся централизованным в `backend/src/ai/dto/ai-params.dto.ts`; это не runtime-хардкод этапов, а источник истины для поддерживаемых моделей.
- Для этапов `planning`, `validation`, `query rewrite` и `fact extraction` сохранены специальные температуры и лимиты токенов, но модель и провайдер теперь резолвятся от пользователя.
- Если пользователь выберет модель, которая хуже держит structured JSON или validation-сценарии, качество этих этапов может просесть — это сознательное следствие нового требования использовать именно выбранную модель на всех стадиях.
