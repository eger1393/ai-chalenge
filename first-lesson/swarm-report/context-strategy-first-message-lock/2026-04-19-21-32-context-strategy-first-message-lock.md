# Отчёт по задаче: редактирование стратегии контекста до первого сообщения и обновление RAG-подписей

## Задача

- разрешить менять стратегию контекста у пустого диалога
- после первого сообщения зафиксировать стратегию и запретить её изменение
- убрать на фронтенде устаревшие подписи про `strict RAG`
- подтвердить на backend, что ответ теперь разрешён не только по данным из RAG

## Что сделано

### Блокировка стратегии после первого сообщения

- На frontend стратегия теперь считается редактируемой, пока у диалога нет сообщений
- После отправки первого сообщения интерфейс сразу фиксирует стратегию
- Для пустого уже созданного диалога смена стратегии сохраняется через `PATCH /conversations/:id/context`
- В панели параметров подпись изменена с общего `Зафиксирована для этого диалога` на точное `Зафиксирована после первого сообщения`

### Backend-защита контракта

- В `ContextService.updateStrategy()` добавлена серверная проверка: если в диалоге уже есть сообщения и стратегия меняется, backend возвращает конфликт
- Это закрывает обход через ручной API-вызов и синхронизирует продуктовый контракт с поведением интерфейса

### RAG-подписи на frontend

- В debug-панели блок `Строгий RAG-режим` переименован в нейтральный `RAG-контракт ответа`
- Подпись теперь явно говорит, что ответ формируется всегда, а RAG показывает степень покрытия
- `План strict RAG` переименован в `План RAG-ответа`

## Верификация backend-контракта RAG

Подтверждено по коду backend:

- `step-orchestrator.service.ts` в `tryRepairStrictRagPlanning()` для `INSUFFICIENT` синтезирует `responseMode: 'ANSWER'`
- `step-runner.service.ts` в `renderStrictRagResponse()` умеет формировать ответ как при частичном покрытии RAG, так и при полном отсутствии данных в RAG
- Следовательно, действующий backend-контракт уже допускает ответ не только по найденным данным из RAG
