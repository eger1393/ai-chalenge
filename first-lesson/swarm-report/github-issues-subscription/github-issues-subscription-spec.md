# Спецификация: Подписка на GitHub Issues через MCP

**Дата:** 2026-04-08  
**Статус:** Draft  
**Фича:** github-issues-subscription

---

## 1. Постановка задачи

Пользователь хочет подписываться на новые issues в GitHub-репозиториях прямо из чата. После подписки система автоматически каждые 5 минут проверяет появление новых issues и отправляет в чат уведомление с AI-сгенерированным summary. Подписка живёт 24 часа или до удаления чата.

---

## 2. Функциональные требования

### 2.1 Подписка

- **Scope:** подписка на весь репозиторий (все новые issues), не на конкретный issue
- **Инициация:** пользователь пишет в чат (например, "подпиши меня на issues owner/repo"), LLM распознаёт intent и вызывает MCP tool `subscribe_issues`
- **Лимиты:** без ограничений — любое количество подписок в любом количестве чатов
- **Только публичные репозитории** (токен без доступа к приватным)
- **Валидация при подписке:** MCP проверяет доступность репозитория через GitHub API при создании подписки. Если репо не существует или недоступен — немедленная ошибка

### 2.2 Поллинг и обнаружение новых issues

- MCP-сервер поллит GitHub API каждые 5 минут для каждой активной подписки
- Отслеживаются **только новые issues** (created after last poll). Комментарии, смена статуса, labels — НЕ триггерят уведомления
- MCP хранит timestamp последнего поллинга для каждой подписки

### 2.3 Передача данных MCP → Backend

- **Механизм:** Webhook — MCP-сервер отправляет HTTP POST на бэкенд при обнаружении новых issues
- **Callback URL:** передаётся MCP-серверу через переменную окружения (например, `BACKEND_WEBHOOK_URL`)
- MCP-серверы сейчас не знают о бэкенде (односторонняя связь) — это архитектурное изменение

### 2.4 Обработка на бэкенде

- Бэкенд получает webhook с данными новых issues + `conversation_id`
- Бэкенд вызывает LLM (OpenAI) для генерации summary
- **Контекст LLM:** данные issues (title, body, labels, author, url) + история чата (conversation messages)
- **Формат summary:** Markdown с кликабельными ссылками на issues
- Токены не лимитируются — каждый issue/батч = отдельный LLM-вызов, расход приемлем

### 2.5 Доставка уведомления на фронтенд

- **Механизм push:** необходимо выбрать при реализации (WebSocket / persistent SSE / polling). Сейчас в проекте SSE используется только request-scoped для pipeline. Нужен механизм server-initiated push
- **Тип сообщения:** специальный тип уведомления, визуально отличается от обычных сообщений ассистента
- **Только информационное** — пользователь НЕ может ответить на уведомление напрямую
- **Персистентность:** уведомления сохраняются в БД (таблица `messages` с особым типом), видны при переоткрытии чата
- **Оффлайн:** если пользователь был оффлайн — увидит все пропущенные уведомления при возвращении

### 2.6 Отписка

- **Только автоматическая:** TTL 24 часа + удаление чата
- Явной отписки через UI или чат нет
- TTL проверяется MCP-сервером самостоятельно при каждом цикле поллинга
- Уведомление об истечении подписки НЕ отправляется (тихое удаление)
- **При удалении чата:** бэкенд явно вызывает MCP tool `unsubscribe` для всех подписок этого чата

### 2.7 Индикатор подписок в чате

- **Расширенный индикатор** в UI чата:
  - Список репозиториев с активными подписками
  - Остаток TTL для каждой подписки
  - Количество полученных уведомлений

## 3. Хранение данных

### 3.1 MCP-сервер — PostgreSQL (тот же инстанс что у бэкенда)

MCP-сервер использует тот же PostgreSQL из docker-compose для персистентного хранения подписок. Это обеспечивает:
- Выживание подписок при рестарте MCP-контейнера
- Не нужен отдельный volume для хранилища MCP

**Данные подписки (минимум):**
- `id` — идентификатор подписки
- `conversation_id` — ID чата (для привязки и webhook)
- `repository` — owner/repo
- `created_at` — время создания (для расчёта TTL)
- `last_polled_at` — время последнего поллинга
- `last_known_issue_id` или `last_polled_issues_since` — маркер для определения новых issues

### 3.2 Backend — PostgreSQL

- Уведомления сохраняются в таблицу `messages` с отдельным типом/статусом (notification)
- Нужно расширить схему messages или добавить тип сообщения

### 3.3 GitHub Token

- Новая env-переменная для github-explorer-mcp (например, `GITHUB_TOKEN`)
- Токен с scope `public_repo` (только публичные репозитории)
- Токен нужно создать: GitHub → Settings → Developer settings → Personal access tokens → Generate new token (classic) → scope: `public_repo`

## 4. Новые MCP Tools

### 4.1 `subscribe_issues`

**Параметры:**
- `repository` (string, required) — формат `owner/repo`
- `conversation_id` (string, required) — ID чата для привязки

**Поведение:**
- Проверяет доступность репозитория через GitHub API
- Если недоступен — возвращает ошибку
- Создаёт запись подписки в PostgreSQL
- Запускает поллинг для этой подписки

**Возвращает:** подтверждение подписки или ошибку

### 4.2 `unsubscribe_issues`

**Параметры:**
- `subscription_id` (string) или `conversation_id` (string) — для удаления конкретной или всех подписок чата

**Поведение:**
- Удаляет подписку из PostgreSQL
- Останавливает поллинг

### 4.3 `list_subscriptions`

**Параметры:**
- `conversation_id` (string, required)

**Возвращает:** список активных подписок с TTL и статистикой

## 5. Новый Webhook Endpoint (Backend)

### `POST /api/webhooks/mcp/issues`

**Payload:**
```json
{
  "conversation_id": "uuid",
  "repository": "owner/repo",
  "subscription_id": "uuid",
  "issues": [
    {
      "number": 123,
      "title": "...",
      "body": "...",
      "labels": ["bug", "critical"],
      "author": "username",
      "url": "https://github.com/owner/repo/issues/123",
      "created_at": "2026-04-08T12:00:00Z"
    }
  ]
}
```

**Поведение:**
1. Проверить что `conversation_id` существует; если нет — ответить MCP статусом `410 Gone` (сигнал отписаться)
2. Вызвать LLM с контекстом чата + данными issues
3. Сохранить результат как notification-сообщение в messages
4. Отправить push-уведомление на фронтенд

## 6. Edge Cases

| # | Сценарий | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Чат удалён, подписка ещё активна в MCP | MCP шлёт webhook → бэкенд отвечает 410 → MCP удаляет подписку |
| 2 | MCP-сервер перезапущен | Подписки восстанавливаются из PostgreSQL, поллинг возобновляется |
| 3 | Подписка на несуществующий/приватный репо | Ошибка при создании подписки (до начала поллинга) |
| 4 | GitHub API rate limit исчерпан | MCP должен корректно обработать 429, пропустить цикл поллинга, не терять подписку |
| 5 | За один интервал появилось много issues (>20) | Все передаются в одном webhook, один LLM-вызов на батч |
| 6 | Пользователь оффлайн | Уведомление сохраняется в БД, отображается при возвращении |
| 7 | Дубликат подписки (тот же репо в том же чате) | Не создавать дубликат, вернуть существующую подписку |
| 8 | TTL истёк | MCP тихо удаляет подписку, поллинг прекращается, индикатор обновляется |
| 9 | Backend недоступен при webhook | MCP ретраит? Теряет данные? (определить при реализации) |
| 10 | Одновременный поллинг по многим подпискам | Нужна очередь/throttling чтобы не превысить GitHub rate limit |

## 7. Риски

| # | Риск | Severity | Описание |
|---|------|----------|----------|
| 1 | **Архитектурный разворот MCP** | HIGH | MCP протокол — request-response. Webhook от MCP к бэкенду — это выход за рамки стандартного MCP. MCP-сервер становится не просто "tool provider", а активным сервисом с фоновыми задачами |
| 2 | **Push-механизм на фронтенд** | HIGH | Сейчас нет server-initiated push. Нужно внедрять WebSocket или persistent SSE — это затрагивает всю архитектуру клиент-сервер коммуникации |
| 3 | **GitHub Rate Limit** | MEDIUM | При масштабировании подписок (10+ активных) — 120+ запросов/час. С токеном (5000/час) терпимо, но нужен мониторинг |
| 4 | **Стоимость LLM-вызовов** | MEDIUM | Каждое уведомление = вызов OpenAI с историей чата. При активных репозиториях расход токенов может быть значительным |
| 5 | **MCP ↔ PostgreSQL** | MEDIUM | MCP-сервер получает прямой доступ к PostgreSQL. Нужно изолировать таблицы/схему, чтобы MCP не мог читать данные бэкенда |
| 6 | **Consistency** | LOW | Подписки в PostgreSQL, но поллинг in-memory (таймеры). При старте нужно восстановить таймеры из БД |

## 8. Definition of Done

- [ ] MCP tool `subscribe_issues` создаёт подписку с валидацией репозитория
- [ ] MCP tool `unsubscribe_issues` удаляет подписку
- [ ] MCP tool `list_subscriptions` возвращает активные подписки чата
- [ ] MCP поллит GitHub API каждые 5 минут для активных подписок
- [ ] MCP отправляет webhook на бэкенд при обнаружении новых issues
- [ ] Подписки персистентно хранятся в PostgreSQL, переживают рестарт MCP
- [ ] Бэкенд принимает webhook, вызывает LLM с контекстом чата, генерирует Markdown summary
- [ ] Бэкенд сохраняет уведомление как специальный тип сообщения в `messages`
- [ ] Фронтенд получает push-уведомления без действий пользователя
- [ ] Уведомление отображается как специальный визуальный блок (не обычное сообщение)
- [ ] При переоткрытии чата видны все прошлые уведомления
- [ ] Расширенный индикатор подписок в чате (репо, TTL, кол-во уведомлений)
- [ ] При удалении чата бэкенд вызывает `unsubscribe` для всех подписок
- [ ] TTL 24ч — MCP тихо удаляет просроченные подписки
- [ ] Orphan webhook (чат удалён) → бэкенд отвечает 410 → MCP отписывает
- [ ] Ошибка при подписке на несуществующий/недоступный репозиторий
- [ ] GitHub token добавлен в env MCP-сервера
- [ ] `BACKEND_WEBHOOK_URL` добавлен в env MCP-сервера

## 9. Открытые вопросы (для стадии реализации)

1. **Push-механизм фронтенда:** WebSocket vs persistent SSE vs polling — выбрать при реализации
2. **Retry-политика webhook:** что делать если бэкенд недоступен при отправке webhook
3. **Схема/namespace в PostgreSQL:** как изолировать таблицы MCP от таблиц бэкенда
4. **Модель LLM для summary:** та же что в чате или отдельная (дешевле)?
5. **Аутентификация webhook:** нужен ли shared secret между MCP и бэкендом?
