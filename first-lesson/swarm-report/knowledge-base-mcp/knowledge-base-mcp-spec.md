# Спецификация: Knowledge Base MCP

## Краткое описание задачи

Нужно добавить новый MCP-сервер "база знаний" в отдельной папке и отдельном Docker-контейнере. Сервер должен сохранять, редактировать и отдавать информацию по тегам. Данные общие для всех пользователей и хранятся в PostgreSQL в отдельной БД.

## Контекст и допущения

- Проект уже использует Docker Compose и PostgreSQL.
- Новый сервис должен быть встроен в существующую инфраструктуру проекта.
- Допустимое содержимое записи: текст и структурированный JSON.
- Основная сущность хранения: одна запись может иметь несколько тегов.
- Каждый тег уникален в системе и однозначно указывает на одну запись.
- Нагрузка ожидается маленькая, тегов будет мало.
- Запись адресуется по тегу; любой тег записи можно использовать для чтения, полной замены и удаления.
- Требование касается постановки задачи; реализационные детали пока не зафиксированы.

## Пользовательские сценарии

- Пользователь или другой сервис сохраняет информацию с одним или несколькими тегами.
- Пользователь или другой сервис полностью заменяет ранее сохранённую запись.
- Пользователь или другой сервис запрашивает информацию по точному тегу.
- При запросе по тегу пользователь или другой сервис получает одну запись, на которую указывает этот тег.
- Пользователь или другой сервис удаляет запись, когда она больше не нужна.
- Пользователь или другой сервис получает список всех доступных тегов отдельной операцией.

## Ограничения

- Новый MCP-сервер должен жить в отдельной папке.
- Новый MCP-сервер должен запускаться в отдельном Docker-контейнере.
- Данные должны храниться в PostgreSQL.
- Для нового сервиса нужна отдельная БД в уже существующем PostgreSQL.
- Информация общая для всех пользователей, без пользовательской изоляции.
- Формат записи ограничен текстом и JSON.
- Редактирование записи выполняется только как полная замена, без частичных патчей.
- Поиск выполняется только по точному совпадению тега.
- Отдельная операция должна возвращать список тегов.
- Операции создания, редактирования и удаления доступны любому авторизованному вызову.
- История изменений и версии записей не требуются; хранится только текущее состояние.
- Явные лимиты на размер записи и количество тегов на старте не требуются.
- Минимальный контракт MCP-инструментов: `create_entry`, `get_by_tag`, `replace_by_tag`, `delete_by_tag`, `list_tags`.

## Риски

- Не определены правила обновления, удаления и конфликтов данных.
- Отсутствие лимитов на размер данных может привести к неконтролируемому росту объёма записей, даже при низкой нагрузке.
- Общий доступ на запись для любого авторизованного вызова повышает риск случайной порчи данных.
- Нужно чётко определить поведение при попытке создать запись с уже существующим тегом, потому что тег уникален в системе.

## Пограничные случаи

- Запрос по несуществующему тегу.
- Несколько тегов у одной записи.
- Обновление записи, которой ещё нет.
- Попытка создать запись с уже существующим тегом.
- Пустой тег или пустое содержимое.
- Большой объём данных в одной записи.
- Несовместимые форматы данных в разных записях.

## Критерии приёмки / DoD

- В проекте описан новый MCP-сервис "база знаний" как отдельная задача.
- Зафиксированы правила хранения и поиска данных по тегам.
- Зафиксировано, какая сущность является основной: тег, запись или набор записей.
- Зафиксировано, что тег уникален и однозначно адресует запись.
- Зафиксировано, что любой тег записи может использоваться для чтения, обновления и удаления.
- Зафиксировано, что поиск идёт только по точному тегу и есть отдельная операция списка тегов.
- Зафиксированы операции создания, чтения, обновления и удаления.
- Зафиксировано, что формат записи ограничен текстом и JSON.
- Зафиксировано, что структура данных ограничена текстом и JSON, а явные лимиты на размер и количество тегов пока не вводятся.
- Зафиксирована модель доступа: писать может любой авторизованный вызов.
- Зафиксировано, что версии и история изменений не ведутся.
- Зафиксирован минимальный контракт MCP-инструментов: `create_entry`, `get_by_tag`, `replace_by_tag`, `delete_by_tag`, `list_tags`.
- Зафиксированы правила ошибок и поведение в пограничных случаях.
- Зафиксированы требования к выкладке и проверке после запуска.
